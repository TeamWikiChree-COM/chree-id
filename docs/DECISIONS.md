# 決定事項

実装していて問題を踏み、その結果として決まったもの。知らずに触ると事故になるので、新しいコードでも同じように書く。

設計全体の方針は [ARCHITECTURE.md](ARCHITECTURE.md)、用語は [ACCOUNTS.md](ACCOUNTS.md) を参照。

## 認証

### ログインできるかは `isSuspended()` だけで判定する

ログインの可否を見ている箇所が10以上ある。退会用の判定を別に足すと、新しい認証経路を足したときに片方しか見ない取りこぼしが起きる。

そのため退会では `deleted_at` と `suspended_at` を両方立てている。退会を取り消すときも両方戻す。

### 認証が成立したかの判定は拡張できないようにする

`AuthenticationPolicy` はすべての認証経路が通る場所なので、差し替えやプラグインの口を作らない。口を作ると、そこから判定を迂回できてしまう。

### 認証の成否は必ず監査ログに残す

どの経路でも、認証の成否は監査ログ (`Audit`) を通す。記録するかどうかを選べるようにしない。どの経路で入られたかを後から追えないと、乗っ取りに気づけず、調べることもできない。

### 外部IdP の `email_verified` を安易に信じない

検証済みと言い切れないアドレスを検証済みとして扱うと、被害者のアドレスで作った外部アカウントから、被害者の既存アカウントに入れてしまう。

外部IdP から受け取るときも、サービスへ渡すときも、本当に到達を確かめたものだけを検証済みにする。

### 統合の根拠は「両方を証明できたか」

メールアドレスが一致しただけでアカウントを寄せない。同じアドレスを使う別人のアカウントも普通にある。一致は候補として見せるだけにして、統合は本人が両方の認証を通したときに行う。

### ServiceAccount を裏で既存アカウントに寄せない

サービスからの発行 (`IssueServiceAccount`) では、アドレスが一致していても既存の UserAccount に寄せない。寄せるかどうかは本人が決める。

## 表示と失敗

### 失敗の理由を1つの文言に潰さない

原因ごとに理由を返す。「ログインできませんでした」の1つに潰すと、利用者も開発者も直しかたが分からない。

例外として、アカウントの有無が分かってしまう場面 (ログイン、パスワード再設定) では、総当たりで登録済みかを調べられないよう文言をそろえる。

## データ

### 数える条件と消す条件でクエリを共有する

「何件消えます」と画面に出す処理と、実際に消す処理で条件を別々に書かない。食い違うと、表示した件数と消えた件数がずれる。

例: `PruneTokens`、`PurgeDeletedAccounts`

### `sub` は ServiceAccount に持たせる

`auth_identity_id` は統合で書き換わる。`sub` をそこから作ると、統合した瞬間にサービスから見て別人になる。

## サービスとの連携

### サービス側の画面は変えない

既存サービスの利用体験はできるだけ保つ。たとえば DokuFarm のログインフォームはそのままで、パスワードの照合先だけを ChreeID に差し替えている。

### OIDC のプロトコル部分は差し替えられるようにしない

仕様が RFC で決まっているので、変える余地が無い。拡張したくなったら、それは OIDC の外 (scope や claims の追加) で行う。

### サービス間のデータ連携はしない

Wiki のインポートなど、サービスの中身を別のサービスへ移す処理は ChreeID に持たせない。持たせると、ページの形式や権限といった各サービスの内部仕様を ChreeID が知る必要が出て、サービスの API が変わるたびに ChreeID を直すことになる。

本体の仕事は「同じ人である」ことを保証するところまで。データの連携が必要になったら、[プラグイン](PLUGIN.md) として作るか、ChreeID でログインする別のアプリとして作る。プラグインなら、サービスの API が変わっても直すのはプラグインだけで済む。
