# ドキュメントの書き方
`docs/` にドキュメントを足すときの決まり。新しく書くときは [templates/](templates/) のひな形をコピーして始める。

## どこに書くか

| 書きたいこと | 場所 |
| --- | --- |
| プロジェクトの概要、すぐ動かす手順 | ルートの `README.md` (大まかに。詳しいことは docs へリンクする) |
| 1つのテーマの詳しい説明 | `docs/<テーマ>.md` |
| 用語の定義 | `docs/term/<ドメイン>.md` |
| プラグインの作り方 | `docs/PLUGIN.md` |
| 個々のプラグインのこと | 各プラグインの `plugins/<名前>/README.md` |
| API の細かい仕様 | OpenAPI (`app/Modules/ApiDocs/`)。docs には概要と場所だけ書く |

1ファイル1テーマにする。既存のファイルに収まらないテーマなら新しく作る。読みたくない人の負担を減らすため、別の話題は別のファイルに分ける。

## ファイル名
特に指定するわけではないが、以下のようにするのが好ましいだろう。

| 種類 | 形 | 例 |
| --- | --- | --- |
| `docs/` 直下 | 英大文字 | `ARCHITECTURE.md`、`DEPLOY.md` |
| `docs/term/` | 英小文字、単語はハイフンでつなぐ | `account-operation.md` |

## 読み手
リポジトリしか見られない、初めて ChreeID に関わる開発者を想定する。
- 略語やChreeID独自の言葉は、初出で意味を書くか [用語リスト](term/README.md) へリンクする

## 書き方（推奨）
- 3つ以上並ぶものや、項目ごとに説明が付くものは表にする
- 決まりごとには理由を書く。理由の無い決まりは守られないし、変えてよいかも判断できない
- 書き方の決まりは GOOD / BAD の例を並べる
- クラス名やファイルを挙げるときは、実在するものを使う。できる限り、消えたら直す

## リンク
- 相対パスで書く (`[API](API.md)`、`[用語リスト](term/README.md)`)
- 新しいファイルを作ったら、[docs/README.md](README.md) の目次とルートの `README.md` の案内表に足す

## 更新
- コードを変えて内容がずれたら、同じ変更の中でドキュメントも直す
- 「現状とのずれ」のような時点で変わる情報には日付を付ける (例: `(2026-09-26 時点)`)
